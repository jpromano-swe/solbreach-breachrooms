## Report

# Root + Impact

## Description
The `approve_task` instruction allows the trusted reviewer to approve a task while supplying an arbitrary `provided_category_config` and `provided_escrow_vault`.

The task already stores its expected `category_config`, `escrow_vault`, and `payout_mint` when it is created. However, during approval, the program does not verify that the provided category config belongs to the task, belongs to the same protocol, or matches the task’s originally configured payout route.

As a result, individually valid accounts can be mixed into an invalid relationship, and the task’s payout route can be overwritten during approval.

## Root Cause
In `approve_task`, the program only checks:

- the reviewer matches `protocol.trusted_reviewer`
- the task status is `InReview`

It does not check that:

- `provided_category_config.key() == task.category_config`
- `provided_category_config.protocol == task.protocol`
- `provided_escrow_vault.key() == provided_category_config.default_escrow_vault`
- `provided_category_config.payout_mint == task.payout_mint`

```rust
task.status = TaskStatus::Approved;
task.escrow_vault = ctx.accounts.provided_escrow_vault.key();
task.payout_mint = ctx.accounts.provided_category_config.payout_mint;
```

Risk
Likelihood:
- This occurs whenever approve_task is called with a valid reviewer and a task in InReview, while the caller supplies a different valid category config or escrow vault.
- The account constraints only require task.has_one = protocol; they do not bind provided_category_config or provided_escrow_vault to the task’s stored route.

Impact:
- An approved task can have its payout route changed from the originally configured escrow vault to a caller-supplied vault.
- The protocol can mark a task as approved while storing a mismatched payout mint and escrow relationship, corrupting payout accounting and enabling funds or rewards to be routed through the wrong configuration.

## Proof of Concept
```rust
// 1. Create task A with category_config_A, escrow_vault_A, and payout_mint_A.
// 2. Move task A into InReview by calling accept_task.
// 3. Call approve_task with:
//    - task = task_A
//    - provided_category_config = category_config_B
//    - provided_escrow_vault = escrow_vault_B
// 4. The instruction succeeds because it only checks reviewer and status.
// 5. task_A is now Approved, but its payout route has been overwritten.

task.status = TaskStatus::Approved;
task.escrow_vault = provided_escrow_vault_B;
task.payout_mint = category_config_B.payout_mint;
```

## Recommended Mitigation
```rust
require_keys_eq!(
    ctx.accounts.provided_category_config.key(),
    task.category_config,
    BreachRoomError::InvalidRoute
);

require_keys_eq!(
    ctx.accounts.provided_category_config.protocol,
    task.protocol,
    BreachRoomError::InvalidRoute
);

require_keys_eq!(
    ctx.accounts.provided_escrow_vault.key(),
    ctx.accounts.provided_category_config.default_escrow_vault,
    BreachRoomError::InvalidRoute
);

require_keys_eq!(
    ctx.accounts.provided_category_config.payout_mint,
    task.payout_mint,
    BreachRoomError::InvalidRoute
);
```
